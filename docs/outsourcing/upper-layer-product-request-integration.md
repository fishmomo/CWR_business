# 上层产品统一请求集成外包任务书

## 1. 任务状态与职责

- 状态：检查点 1 设计已定稿；外包人员收到用户开工指令后进入检查点 2。
- 架构设计负责人：Codex。
- 实现负责人：外包人员。
- 临时监工：Codex，负责维护实施设计、代码审查、验收复核和书面反馈，不负责本阶段编码。
- 试点范围：仅限 `cloud_water_single_year` 单年云水资源报告。
- 后续阶段：多年报告统一请求集成，当前不在本任务范围内。

检查点 1 的权威实施设计见
`docs/outsourcing/checkpoint-1-final-implementation-design.md`。外包不得采用
`checkpoint-1-contractor-design-rejected.md` 中被否决的方案，也不得自行更换架构。

## 2. 现状与目标

当前存在两套入口：

- 通用入口 `cwr-engine --request` 使用统一业务请求，负责数据源、必要区域、时间、变量和通用输出。
- 单年报告入口 `cwr-engine --workflow-spec` 使用专题工作流配置，负责年/月产品发现、专题指标、图件和 DOCX 报告。

本阶段要让单年报告消费统一请求或其清单，不再独立维护重复的数据源、区域、年份和通用产物选择；专题公式、图件规则、报告模板及事务发布行为保持不变。目标路径为：

```text
统一业务请求/请求集合
  -> 标准请求上下文与产物清单
  -> 既有云水资源共享计算内核
  -> 既有专题图件与报告 profile
  -> 事务式发布完整报告
```

## 3. 已冻结的设计决策

单年报告需要一个年度产品和该年 12 个月度产品；现有统一请求一次只表达一种源产品时间尺度。检查点 1 已确定由上层产品声明请求集合，共享数据源和区域，并分别包含 `annual` 与 `monthly` 两个有明确角色的标准请求。

实施必须满足：

- 不进行日到月、月到年等跨尺度重采样，始终读取已有日、月、年源产品。
- 不把专题公式复制到统一请求编译器中。
- 不新建第二套数据发现、mask 或计算内核。
- 区域输入仍为必要输入，SHP、已有 mask 或边界框都必须形成统一的内部 mask；同一产品任务应复用该 mask。
- 标准请求清单与报告清单之间的引用关系、最终路径和失败行为必须清楚。

## 4. 实施范围

本阶段包含：

- 为单年报告定义统一请求或请求集合的上层配置协议，并提供版本号和严格校验。
- 让统一请求成为数据源、必要区域、目标年份和通用变量选择的权威来源。
- 将标准请求产物清单接入既有单年专题流程，专题派生指标仍由共享云水资源内核生成。
- 保留现有 `cloud_water_single_year` 配置的兼容入口，给出迁移示例和弃用边界，不在本阶段强制删除。
- 维持现有事务发布规则：任一步失败不得覆盖已有正式报告，也不得留下半成品正式目录。
- 为新入口补充合成测试、兼容测试、失败测试和一次真实 2025 数据验收。

本阶段不包含：

- 多年报告接入。
- 新增或修改物理公式、变量、图型、图件样式、业务语段和 DOCX 模板。
- 跨尺度重采样、缓存、调度、重试、分布式执行、GUI 或 Web UI。
- 清理历史兼容入口，或重写已通过验收的共享计算内核。

## 5. 外包必须回传的材料

### 检查点 1：设计回传，编码前

状态：已完成。协议、执行链、mask 复用、清单关系、事务边界、允许改动和验收要求均以 `checkpoint-1-final-implementation-design.md` 为准。

### 检查点 2：实现回传，代码完成后

- 独立提交号和精简的 diff 摘要。
- 新入口的完整执行命令和合成产物路径。
- 新增测试列表及结果，至少覆盖正常、缺年产品、缺任一月产品、非法区域和发布失败。
- 旧入口兼容测试结果。
- 说明哪些重复逻辑被收敛，以及如何证明没有复制计算公式、数据发现或 mask 逻辑。
- 所有已知问题、临时兼容代码和后续清理项；不得隐瞒失败用例。

### 检查点 3：真实数据终验

- 使用官方 2025 年产品和既有内蒙古中西部区域的准确命令、配置及产物路径。
- 新旧入口的指标、表格、空间 NetCDF、图件和 DOCX 对比结果；数值差异必须给出容差和原因。
- DOCX 结构检查结果：占位符清零、表格/图件槽完整、文件可打开。
- 完整测试命令与结果，以及干净的 `git status`。
- 若图件字节不一致，必须提交逐图视觉对比和差异原因；本阶段不得借机改变已验收样式。

## 6. 监工审查标准

监工每轮只给出以下三种结论之一：`通过`、`修改后复审`、`拒绝`。问题按严重度记录：

- P0：数据错误、跨尺度重采样、破坏正式产物、绕过必要 mask、泄露敏感数据等，必须立即停止。
- P1：重复实现核心逻辑、协议职责混乱、兼容性或事务性回归、关键测试缺失，修复后才能进入下一检查点。
- P2：文档、命名、低风险测试或维护性问题，可在当前检查点内整改。

每次监工反馈固定包含：

```text
审查轮次：
基线/候选提交：
结论：通过 / 修改后复审 / 拒绝
P0/P1/P2 问题（含文件和行号）：
已执行验证及结果：
下次必须回传的材料：
是否允许进入下一检查点：是 / 否
```

出现以下任一情况直接不予验收：

- 报告流程重新直接依赖历史 CSV、空间分析 NC 或显式历史 PNG。
- 通过重采样代替读取既有年/月源产品。
- 复制既有专题公式、产品发现、mask 编译或图件实现形成第二套内核。
- 改变已验收公式、图件或模板，却没有单独授权。
- 失败后正式输出目录被部分覆盖，或清单记录临时目录路径。
- 只陈述“结果一致”，未提供命令、路径、测试和对比证据。

## 7. 验收与截止条件

最低验证命令为：

```powershell
conda run -n cwr_py312 python -m pytest -p no:cacheprovider -q
```

阶段仅在以下条件全部满足后截止：新协议及迁移示例完成；单年新旧入口均可运行；真实 2025 报告通过数值、图件和 DOCX 验收；失败保持事务安全；完整测试通过；变更形成一个独立、可回滚的提交。截止后停止继续扩展，不自动进入多年报告阶段。
